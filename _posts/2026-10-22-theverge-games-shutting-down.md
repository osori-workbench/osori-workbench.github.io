BioWare가 문을 닫는다는데, 이유를 경영진 탓으로만 돌리면 반만 본 거다. 개발자 입장에서 같이 볼 게 하나 더 있다. 엔진이다.

> 게임 엔진은 "그리기, 입력, 물리, 리소스 관리"를 매번 새로 짜기 싫어서 쌓아 올린 재사용 덩어리다.
> 엔진을 직접 만들면 통제권이 생기지만 유지비가 영원히 따라붙는다. 사서 쓰면 빠르지만 남의 로드맵에 묶인다.
> BioWare는 한동안 상용 엔진을 쓰다가 EA 사내 엔진으로 옮겼고, 그 이사 비용을 여러 번 치렀다고 알려져 있다.

## 엔진이라는 말이 없던 시대

초창기 게임은 게임마다 처음부터 다 짰다. 화면에 점 찍는 코드, 키보드 읽는 코드, 시간 재는 코드가 전부 게임 하나 전용이었다.

그래서 다음 게임을 만들 때 하는 일은 이전 프로젝트 폴더를 통째로 복사해서 필요 없는 부분을 지우는 것이었다. 재사용이라고 부르기엔 민망한 수준이다.

이때도 모든 게임이 공통으로 가진 구조가 하나 있었다. 게임 루프다. 입력을 읽고, 상태를 갱신하고, 화면에 그리고, 이걸 계속 반복한다.

## 그 방식 그대로 만들어 보기

아래는 고정 시간 간격으로 상태를 갱신하는 가장 단순한 루프다. 화면 대신 콘솔에 출력한다.

```python
# Python 3.x, 표준 라이브러리만 사용
import time

STEP = 1 / 30                      # 갱신은 1/30초 단위로 고정
state = {"x": 0.0, "hp": 100.0, "t": 0.0}

def update(s, dt):
    s["x"] += 2.0 * dt             # 캐릭터가 오른쪽으로 이동
    if s["x"] > 3:                 # 3칸 넘으면 함정 구역
        s["hp"] -= 10 * dt

def render(s):
    print(f"t={s['t']:.1f}  x={s['x']:.1f}  hp={s['hp']:.0f}")

acc, prev, shown = 0.0, time.perf_counter(), -1
while state["t"] < 3.0:
    now = time.perf_counter()
    acc += now - prev
    prev = now
    while acc >= STEP:             # 밀린 시간만큼 갱신을 따라잡는다
        update(state, STEP)
        state["t"] += STEP
        acc -= STEP
    if int(state["t"] * 2) != shown:   # 0.5초마다 한 번 출력
        shown = int(state["t"] * 2)
        render(state)
    time.sleep(0.005)
```

여기서 아픈 지점은 이렇다.

- 함정, 이동 속도 같은 규칙이 `update` 안에 하드코딩돼 있다. 규칙이 늘면 `if`가 끝없이 늘어난다.
- 캐릭터가 하나만 있다는 가정이다. 100개가 되면 상태 관리부터 다시 짜야 한다.
- 대사, 선택지, 퀘스트 같은 RPG 데이터는 이 구조에 자리가 없다. 전부 코드에 박아야 한다.

## 그래서 어떻게 굳어졌나

```mermaid

    B --> C["엔진 + 툴 분리"]
    C --> D["상용 엔진 라이선스"]

```

위 그림은 왼쪽에서 오른쪽으로 읽는다. 마지막에 길이 둘로 갈라진다는 게 핵심이다.

첫 번째 단계는 코드 복붙이 지겨워서 공통 부분을 라이브러리로 뽑는 것이다. 이러면 중복은 줄지만 프로그래머만 건드릴 수 있다. 레벨을 하나 옮기려 해도 기획자가 프로그래머를 불러야 한다.

두 번째 단계는 데이터와 툴을 분리하는 것이다. 맵 에디터, 스크립트, 리소스 파이프라인이 생기고 기획자가 직접 콘텐츠를 만들게 됐다. 대신 엔진이 거대해지고, 엔진 전담팀이 필요해졌다.

세 번째 단계는 그 전담팀 비용을 아끼려고 엔진을 사서 쓰는 것이다. 90년대 후반부터 Unreal 같은 엔진이 라이선스로 팔렸고, 2000년대 중반에는 Unity도 나왔다. 대신 엔진이 안 맞는 장르를 만들 때는 구조를 뜯어고쳐야 하고, 엔진 회사의 방향이 곧 내 일정이 된다.

네 번째 단계는 대형 퍼블리셔가 엔진을 사내에 두는 것이다. EA의 Frostbite가 대표적이다. 원래 DICE가 슈팅 게임용으로 만든 엔진이다.

| 방식 | 장점 | 한계 |
|---|---|---|
| 게임마다 직접 | 완전한 통제 | 매번 재발명 |
| 자체 엔진 | 장르에 최적화 | 엔진팀 유지비 |
| 상용 엔진 | 빠른 시작, 인력 풍부 | 로드맵 종속, 수수료 |
| 퍼블리셔 사내 엔진 | 그룹 내 기술 공유 | 다른 장르엔 안 맞을 수 있음 |

## 지금은 어떤가

BioWare 시리즈 초기에는 상용 엔진 기반이 있었고, Andromeda 무렵부터는 Frostbite를 썼다. 당시 보도로는 슈팅 위주로 만든 엔진에 RPG에 필요한 기능이 부족해서 개발이 힘들었다고 한다. 인벤토리나 대화 같은 걸 엔진에서 새로 얹어야 했다는 얘기다. 앞의 샘플 코드의 세 번째 아픈 지점이 그대로 비싼 버전이 된 셈이다.

물론 엔진만으로 스튜디오가 망하진 않는다. 기사에 나온 대로 Anthem의 라이브 서비스 도박, 인력 이탈, 판매 부진, 인수 후 구조조정이 겹쳤다. 엔진은 그중 개발 속도를 깎은 한 요소로만 봐야 정확하다.

지금 선택지는 셋이다. Unreal이나 Unity 같은 상용 엔진은 인력 구하기가 쉽지만 로드맵이 남의 것이다. 사내 엔진은 그룹 안에서 기술을 공유하기 좋지만 장르가 다르면 고생한다. 직접 만드는 건 강력하지만 소규모 팀이 감당할 수준이 아니다.

엔진은 한번 정하면 바꾸는 비용이 너무 커서 사실상 스튜디오의 운명을 같이 정한다. 그걸 기술 선택 회의에서 가볍게 정하는 곳이 많다는 게 문제다.
